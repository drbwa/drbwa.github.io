§ 4

Cutover

Two things change at once — the site moves to Astro, and the site moves to brunowassermann.com. Order matters for both.

GitHub Pages currently runs its legacy Jekyll builder over master. If the Astro branch merges while that is still true, GitHub tries to build an Astro repository with Jekyll. So the Pages build type is switched first, while master is still the old site — at that point no workflow exists on master, nothing deploys, and the last successful build keeps serving. Then the merge lands and the deploy workflow publishes.

The DNS goes in first of all, because records need time to propagate and GitHub cannot even attempt a certificate until the domain resolves to it. Nothing about the DNS step affects the live site.

The Cloudflare trap — read before touching DNS

Cloudflare proxies new records by default (the orange cloud). GitHub Pages issues its Let's Encrypt certificate through an HTTP challenge that must reach GitHub's servers directly, and a proxied record intercepts it. The symptom is a site that loads over HTTP while Enforce HTTPS stays greyed out forever. Every GitHub-facing record must be created as DNS only (grey cloud). Setting Cloudflare's SSL/TLS mode to Flexible instead of Full produces an infinite redirect loop, which is the other half of the same trap.

4.1   Register the domain and point it at GitHub

Buy brunowassermann.com through Cloudflare Registrar (Domain Registration → Register Domains). Cloudflare sells at wholesale cost with no renewal markup, includes WHOIS privacy, and puts the zone in the same account as the DNS, so there is nothing to delegate. Registration creates the DNS zone automatically.

Then add these records in DNS → Records. The four A and four AAAA records are what GitHub documents; every troubleshooting guide assumes them, which is why they are the recommendation here.

One-record alternative

Cloudflare flattens a CNAME at the apex, so a single CNAME @ → drbwa.github.io (DNS only) replaces all eight address records and keeps working if GitHub ever changes its Pages IPs. It is the lower-maintenance option and GitHub explicitly permits ALIAS/ANAME records at the apex. The reason it is not the default recommendation is only that when something goes wrong, every guide you will find describes the eight-record setup. Pick either; do not mix them.

If a record resolves to a Cloudflare address (typically 104.* or 172.67.*) rather than GitHub's, the orange cloud is still on. Turn it off before continuing.

4.2   The switch, the merge, the domain

1

Switch GitHub Pages to Actions

One API call. The site keeps serving its last deployment throughout.

Verify: build_type reads workflow, and drbwa.github.io still loads the old site.

2

Merge the branch

The build output now carries dist/CNAME, so GitHub picks up the custom domain from the deployment itself.

Verify: the "Deploy to GitHub Pages" workflow starts within seconds and goes green.

3

Confirm the custom domain in the Pages settings

Open Settings → Pages. The custom domain field should already read brunowassermann.com, picked up from the CNAME file in the deployment. If it is empty, type it in and save — this triggers GitHub's DNS check.

Verify: the settings page shows a green "DNS check successful".

4

Wait for the certificate, then enforce HTTPS

GitHub requests a Let's Encrypt certificate as soon as the DNS check passes. This usually takes a few minutes and can take up to an hour. Enforce HTTPS stays greyed out until it lands — that is expected, not a fault.

Then tick Enforce HTTPS in Settings → Pages.

If it is still greyed out after an hour

Almost always a proxied record. Confirm with the dig commands in 4.1, set every GitHub-facing record to DNS only, then remove and re-add the custom domain in Settings → Pages to re-trigger the request.

5

Verify the live site on the new domain

Verify: eight 200s, one 404, and every redirect line points at https://brunowassermann.com. Then open the site in a browser and check the theme toggle, one post, and the padlock.

6

Verify the domain with GitHub — do not skip this

An unverified custom domain can be claimed by another GitHub user if this repository is ever deleted, renamed, or unlinked from the domain. Verification is a single TXT record and it removes that risk permanently.

In GitHub → Settings → Pages → Add a domain, GitHub gives you a record of the form _github-pages-challenge-drbwa.brunowassermann.com with a token value. Add it in Cloudflare as a TXT record, then click Verify.

Leave the TXT record in place forever. Removing it un-verifies the domain. Also: never create a wildcard * record on this zone — it reopens the takeover risk even on a verified domain.

7

Point drbwa.com at the canonical domain

Only if you bought it too. A redirect has to pass through Cloudflare's edge, so this zone is the one place the orange cloud is required — the opposite of 4.1.

  • Add drbwa.com to Cloudflare and register it the same way.
  • Create A @ → 192.0.2.1 and A www → 192.0.2.1, both Proxied. That address is reserved documentation space and is never reached; it exists only so Cloudflare has something to proxy.
  • SSL/TLS → Overview → set the mode to Full. Not Flexible.
  • Rules → Redirect Rules → create a rule: when hostname is drbwa.com or www.drbwa.com, redirect to concat("https://brunowassermann.com", http.request.uri.path) with status 301 and "preserve query string" on.
8

Remove the Jekyll files, in their own commit

Only after step 5 passes. The command is in DOC 02 §P6. Keeping it separate is what makes the rollback in §5 a single revert.

9

Tell search engines

Add brunowassermann.com as a property in Google Search Console (the DNS TXT verification method is easiest, since you already control the zone) and submit https://brunowassermann.com/sitemap-index.xml. The old Jekyll site had no sitemap at all, so this is new ground rather than a replacement. GitHub's automatic 301 from drbwa.github.io is what carries the existing link equity across; nothing else is needed for that.

4.3   Optional, later: turn Cloudflare's proxy on

Once the certificate is issued and HTTPS is enforced, you may switch the apex and www records to Proxied to get Cloudflare's CDN and analytics. If you do, set SSL/TLS to Full (strict) first — Flexible causes a redirect loop with GitHub's own HTTPS redirect.

My advice is not to bother. GitHub Pages is already served from a CDN, the site is a few hundred kilobytes of static files, and proxying adds a layer that will silently block the certificate's renewal every ninety days in exactly the way it blocked the first issuance. The one good reason to turn it on is if you want Cloudflare Web Analytics — and that would also settle Q1.

§ 5

Rollback

Two minutes, and it works from any point after cutover. Pick the case that applies.

Case A — the new site is live but wrong

Fix forward. A push to master redeploys in under a minute; that is the whole point of having CI. Only use case B if the site is broken and the fix is not obvious.

Case B — go back to Jekyll

Case C — keep Astro, but back out of the custom domain

These are independent; you can undo the domain without undoing the rebuild.

  1. Delete public/CNAME, set site and SITE_URL and the robots.txt sitemap line back to https://drbwa.github.io (DOC 02 T1.8), commit and push.
  2. Clear the custom domain: gh api -X PUT repos/drbwa/drbwa.github.io/pages -f cname="".
  3. Leave the Cloudflare records and the verification TXT record alone. They cost nothing, and removing the TXT record would un-verify a domain you may want to re-point later.

The drbwa.github.io URL starts serving directly again as soon as the custom domain is cleared.

One thing that is not reversible

Once brunowassermann.com has been indexed and linked, backing out means the reverse redirect does not exist — GitHub redirects github.io → custom domain, never the other way. If you have any doubt about the domain, decide before step 3 of §4.2, not after.

The backstop

If everything else fails, git checkout pre-astro -- . restores the exact tree that was serving before any of this started. The tag is pushed to the remote in DOC 02 T0.1 and should never be deleted.

§ 6

Writing a post

This section is for Bruno, after launch. It is also the content of the new README.md — see §7.

6.1   A new post

One file. The filename becomes the URL: small-model-enough.mdx is served at /blog/small-model-enough/. Use .md for plain prose and .mdx when you want a figure or a chart — the difference is only that .mdx lets you import components.

FieldRequiredNotes
titleyesUp to 80 characters. Becomes the page title and the feed entry.
descriptionyes20–200 characters. Shown under the title in the index and used as the meta description — write it for a stranger.
pubDateyesYYYY-MM-DD. Sorts the index and the feed.
updatedDatenoAdds an "Updated" line to the post.
tagsnoStored and displayed. Tag pages do not exist yet, deliberately.
draftnoDefaults to false. True keeps it out of the build entirely.
A missing field fails the build

That is the schema doing its job. The error names the file and the field.

6.2   A diagram

A fenced mermaid block, in .md or .mdx. Nothing to import; the runtime loads only on pages that have one, and follows the page theme.

Flowcharts, sequence diagrams, state machines, ER diagrams, Gantt charts, timelines, quadrant charts and pie charts are all available. For a rough bar or line chart, xychart-beta will do — but for anything with real data, use §6.4.

6.3   A figure or screenshot

Put the image next to the post in _assets/, import it, and pass it to <Figure>. Importing rather than linking is what gets the image resized, converted and fingerprinted.

width="wide" lets a figure break out past the text column, up to 940px. Leave it off for anything that reads fine at text width. alt is required and is checked in §3.2 — describe what the reader would see, not that it is an image.

6.4   A chart

Charts are static SVG, generated where the data already is — which for you means matplotlib. This keeps the page at zero JavaScript, makes the chart part of the repository rather than a runtime dependency, and means a post from 2026 still renders in 2036.

Export two variants, because a chart drawn for a white page is unreadable on a dark one. The helper below matches the site tokens exactly.

If Image rejects the SVG

Astro treats an imported .svg as both a component and image metadata, so <Image> normally accepts it. If a future version does not, change Figure.astro to emit a plain <img src={src.src} /> for SVG sources. Nothing else needs to change.

Interactive charts are deliberately not supported. If a post genuinely needs one — a reader dragging a threshold to see the cost move — that is a per-post decision: add a small component with client:visible so the JavaScript loads only when the chart scrolls into view, and only on that post. Do not add a charting library globally.

§ 8

Keeping it working

The failure mode for a personal site is not that it breaks; it is that three years pass, a dependency has moved on, and nobody remembers how any of it fitted together. Three habits prevent that.

  • Upgrade on purpose, twice a year. npm outdated, then bump, then open /blog/_pipeline-check/ in npm run dev and look at it. That fixture is the regression test — it is the reason to keep a draft post in the repository forever.
  • Treat a silent diff as a failure. The Astro 7 Sätteri change is the archetype: the build passed, the pages rendered, and the plugins had stopped running. After any Astro major version bump, check the fixture post specifically for maths, diagrams and heading anchors — the three things that fail quietly.
  • Keep CI green on every branch. ci.yml runs the build, the type check and the link check on every push. A red branch is a five-minute problem; a red branch discovered six months later is an afternoon.

Everything else is optional. The site is a few hundred kilobytes of static files with no database, no server and no third-party script — which is exactly what it should be.
