Leaving Jekyll Behind

An audit of drbwa.github.io as it stands in September 2026, a comparison of what could replace it, and the case for rebuilding on Astro 7 with Substack as the distribution channel.

Repo drbwa/drbwa.github.io Branch astro-rebuild Decided 17 Sep 2026 Audience Bruno (review) → implementer (execute)
§ 1

Verdict

Decided

Rebuild on Astro 7, syndicate to Substack

astro 7.3.2 · @astrojs/mdx 8.0.1 · MDX content collections · GitHub Actions → GitHub Pages · brunowassermann.com canonical

Jekyll is not broken in 2026, but it is now a legacy choice whose single remaining advantage — being the thing GitHub Pages builds for you natively — you no longer need, because GitHub Pages has built any static output from GitHub Actions for years. Everything else about the current setup argues for a move: the analytics have been dead since 2023, the stylesheet is a compiled artefact that fights the theme, the blog was never actually started, and you cannot run the site locally without Docker because there is no Ruby on this machine.

Astro is the strongest fit for what you actually want next — Markdown and MDX posts with Mermaid diagrams, figures and charts — because it treats content as a first-class, schema-validated thing, ships zero JavaScript unless a component asks for it, and runs on the Node toolchain you already have installed.

Posts are published here first, as canonical, and then syndicated to Substack for email distribution. The site owns the archive and the URLs; Substack owns the mailing list. Reasoning in § 7, mechanics in DOC 05.

The runner-up is Eleventy, and it is a genuinely reasonable answer if you would rather have less machinery. I say when to pick it in § 3. Hugo is faster than both and irrelevant at this scale. Staying on Jekyll is the only option I would actively argue against, and even then only because of the specific rot listed below rather than anything ideological.

§ 2

What you have today

Eleven files, ten commits, last touched some time ago. It is a stock minima 2.x site with three content pages and no posts. The Pages API reports the site is still built by GitHub's legacy Jekyll builder from master:/. Here is what an audit turns up, worst first.

Broken

Analytics have collected nothing for three years

_config.yml sets google_analytics: UA-126624552-1 and _includes/google-analytics.html loads analytics.js. Universal Analytics stopped processing hits on 1 July 2023 and the analytics.js library is retired. Every visit since then has been unrecorded. This needs a decision, not a port — see Q1.

Broken

Your stylesheet collides with the theme's

assets/main.css is a checked-in copy of minima 2.x's compiled Sass output. Minima also ships assets/main.scss, which compiles to the same /assets/main.css path. Two sources, one output path — Jekyll resolves this with a conflict warning, and the practical effect is that theme upgrades can never reach your CSS. Any styling change today means hand-editing generated code.

Rot

The Gemfile pins you to whatever the legacy builder ships

gem 'github-pages' hard-pins Jekyll, Kramdown, minima and every plugin to the versions GitHub's legacy Pages builder allows — a Jekyll 3.x line that has been frozen for years. You cannot adopt Jekyll 4, and you cannot add a plugin that is not on GitHub's allowlist, without abandoning the legacy builder anyway.

Rot

You cannot build the site on this machine without Docker

There is no Ruby on the box; ruby --version returns nothing. The docker-compose.yml exists precisely to work around that, and it uses the v1 top-level-service schema with no version: key and a bare jekyll/jekyll tag — an image that has not been maintained. Node 24.15.0 and npm 11.12.1 are installed and current.

Gap

The blog does not exist

blog.md declares permalink: /blog/ and says "A curated list of my blog posts." There is no _posts/ directory, no post, and the page is commented out of header_pages so nothing links to it. The feature you most want is the one that was never started — and no amount of tooling fixes that. See the caveat at the end of § 7.

Gap

No CI, no build check, no preview

A push to master is a deploy. If a build breaks, you find out from the live site or a GitHub email. There is no pull-request preview, no link checking, and no way to see a change before the world does.

Gap

Small config bugs

url carries a trailing slash (https://drbwa.github.io/), which Jekyll's own docs warn against and which yields doubled slashes in feed and sitemap URLs. The mastodon: key names medium.com as an instance, which is not a Mastodon instance and which minima 2.x does not render anyway. There is no sitemap and no jekyll-seo-tag, so the site has no canonical URLs, no description meta, and no Open Graph cards.

Gap

The prose has drifted from the truth

The home page still describes AIOps and ML productionisation as the current focus. Your CV says the current focus is agent cost optimisation, and the intervening decade — LakeGuard, ARISE, hybrid data flows, six patents, EuroSys — is not on the site at all. Handled in DOC 03.

Why Astro, specifically

  • Content collections are typed. You declare a Zod schema for post front matter once; a missing description or a malformed date fails the build with a pointer at the file, rather than rendering an empty tag into production. For a site you touch a few times a year, that is the difference between "it still works" and "I have to relearn it".
  • MDX is how charts get in. A chart is not Markdown. In Astro you import a <Chart> or <Figure> component into a post and use it inline, and the JavaScript for it ships only on the pages that use it. That is exactly the "diagrams, figures, charts" requirement, met without a build-your-own step.
  • Zero JS by default. The home page, publications page and any prose-only post ship no JavaScript at all. This matters for a personal site that should still load instantly in ten years.
  • Node, which you already run. Astro 7 requires Node ≥ 22.12.0; you have 24.15.0. No Docker, no Ruby, no second toolchain.
  • It is the most legible stack to a coding agent. You work with Claude Code and Codex. Astro's file-based routing and single-file components are unusually easy for a model to reason about and modify correctly — which, as it turns out, is the fact that settled the whole decision. See § 7.

When to pick Eleventy instead

If the idea of a component model and a Vite build makes you tired, Eleventy 3 is the honest alternative: plain Node, plain templates, no framework concepts, and it will happily render Markdown with Mermaid via a plugin. What you give up is the typed content layer, the built-in image pipeline, and the easy path to an interactive chart. Choose it if you expect to write prose-only posts and want the smallest possible thing to maintain. Everything in DOC 03 (design and copy) transfers unchanged; only DOC 02 would need rewriting.

Why not Hugo

Hugo is the fastest static site generator and its build speed is worth nothing to you — you will have fewer than fifty pages. In exchange you write Go templates and reach for shortcodes whenever content needs to do something a paragraph cannot. It is the right answer for a large documentation site and the wrong shape for a personal site with charts.

§ 4

Risk register

Seven of these are real and one will silently ruin an afternoon if the implementer does not know about it in advance. It is first for that reason.

The one that bites

Astro 7 replaced its Markdown engine, and remark/rehype plugins fail silently. Astro 7 made Sätteri, a Rust Markdown processor, the default. It is not a remark wrapper — it has its own plugin API (mdastPlugins, hastPlugins). If you configure markdown.remarkPlugins or rehypePlugins without installing and selecting @astrojs/markdown-remark, the site still builds, the posts still render, and your plugins simply do nothing. No error. This is the single most reported Astro 7 upgrade failure, and it is exactly the class of bug a lower-capability implementer will not catch. DOC 02 pins the unified processor explicitly for this reason.

R-01

GitHub Pages is still on the legacy Jekyll builder

blocks launch

The Pages API currently reports build_type: "legacy" with source master:/. GitHub will keep trying to run Jekyll over the repo — and an Astro repo has no _config.yml, so it will fail — until the build type is switched to workflow. This is a one-line settings change, but nothing deploys until it happens.

MitigationSwitch Pages to "GitHub Actions" as an explicit, separately-verified step at cutover, not buried inside the build phase. Procedure and the gh api one-liner are in DOC 04 § 4.

R-02

Existing URLs and the feed can break

medium

Today the site serves /, /publications/, /blog/, /404.html and — via jekyll-feed — /feed.xml. Astro's RSS examples default to /rss.xml. Anyone subscribed, and any inbound link, breaks quietly.

MitigationTreat the existing paths as a contract. Keep /publications/ and /blog/, and emit the feed at /feed.xml (optionally also at /rss.xml). DOC 04 includes a URL-parity check that must pass before cutover.

R-03

Mermaid is heavy if you let it be

medium

Mermaid 11 is a large client-side library. Loaded naively it lands on every page, including the ones with no diagram, and undoes the zero-JS advantage that motivated the choice of Astro.

Mitigationastro-mermaid loads the runtime only on pages that contain a mermaid code block. Verify this rather than assume it: DOC 04 has a check that the home page ships no JavaScript.

R-04

Your CV PDF carries your mobile number and home city

resolved

The full CV lists a personal phone number and your town. Putting that PDF on a public, indexed URL publishes both permanently, to scrapers as much as to recruiters.

Resolved — Q3A web CV page at /cv/ with an email address and nothing else; no PDF on the site. DOC 04 § 1.2 makes this a hard check: grep for the phone number and the town across dist/ must return nothing before launch.

R-05

The implementer over-designs it

medium

"Modern and simplistic" is the brief most reliably violated by an eager assistant, which will reach for gradient heroes, card grids and animation. The result is a site that looks like every other generated portfolio.

MitigationDOC 03 specifies the design as fixed tokens, a type scale, and an explicit list of things not to add — so the implementer is applying a system rather than inventing one.

R-06

Cloudflare's proxy stops GitHub from issuing an HTTPS certificate

blocks launch

Cloudflare turns proxying on by default for new records — the orange cloud. GitHub Pages provisions its Let's Encrypt certificate through an HTTP challenge that has to reach GitHub's servers directly, and a proxied record intercepts it. The result is a custom domain that loads over HTTP but where "Enforce HTTPS" stays greyed out indefinitely. Setting Cloudflare's SSL mode to Flexible instead produces an infinite redirect loop.

MitigationCreate every GitHub-facing record as DNS only (grey cloud) and leave it that way until the certificate is issued and HTTPS is enforced. Only then consider turning the proxy on, and only with SSL/TLS set to Full (strict). Step-by-step in DOC 04 § 4.

R-07

Syndication drifts, and Substack becomes the canonical copy

medium

Substack does not let a publisher set an external canonical tag, so every cross-posted piece asserts itself as canonical on substack.com. If you ever post to Substack first, or forget the "originally published at" link, the version that gets cited and linked is the one you do not own. Over a few years that quietly relocates your archive.

MitigationOne rule, stated as a rule rather than a preference: the site publishes first, always. Substack gets a copy afterwards with a link back in the first paragraph. The per-post checklist that enforces this is DOC 05 § 3.

§ 5

Migration at a glance

Seven phases, all of it on a branch. The live site keeps serving the current Jekyll build until phase 6, and the phases are ordered so that the two irreversible steps — the Pages settings change and the branch merge — come last and separately.

The hour estimates below are what this costs a coding model to execute. Your own cost is review time, which is concentrated almost entirely in P3 (the copy) and P5 (looking at the result). That distinction is what changed the plan — see § 7.

P0

Safety net

Tag the current tree, capture the live site's URLs and rendered HTML for later comparison, create the astro-rebuild branch. Nothing is deleted yet.

0.5 h
P1

Scaffold and configure

Astro 7 project, pinned dependencies, the unified Markdown processor, MDX, sitemap, content collection schema, CI workflow. Builds an empty but correct site.

1.5 h
P2

Design system and layouts

Token stylesheet, base layout, header, footer, prose styles, both themes. Applied from DOC 03, not invented.

3 h
P3

Pages and copy

Home, writing index, publications, CV, 404. All prose pasted from DOC 03. Your review lands here.

2 h
P4

Blog pipeline

Post layout, Mermaid, <Figure>, math, syntax highlighting, feed at /feed.xml, the subscribe line and syndication metadata from DOC 05, plus a kitchen-sink fixture post that exercises every one of them.

2.5 h
P5

Test

Build, URL parity against the captured baseline, link check, both themes, keyboard and screen-reader pass, Lighthouse, no-JS check on the home page.

1.5 h
P6

Cutover

Register the domain, add DNS as DNS only, switch Pages to Actions, merge, wait for the certificate, enforce HTTPS, verify live, then remove the Jekyll files in a separate commit so the revert stays clean.

1 h
Rollback

Until P6 the live site is untouched, so rollback is "close the branch". After P6, rollback is two steps: set the Pages build type back to legacy with source master:/, and git revert the merge. Because the Jekyll files are deleted in their own commit after the merge, reverting that one commit restores a working Jekyll site immediately, without touching anything else. The pre-astro tag from P0 is the backstop.

§ 6

Decisions

Five questions were open. Q2, Q3 and Q4 are settled. The remaining two have recommendations the implementer will follow by default if you say nothing.

What replaces the dead analytics?

The Universal Analytics property has recorded nothing since mid-2023. Options: drop analytics entirely; GA4; or a cookieless counter such as Cloudflare Web Analytics or GoatCounter, which needs no consent banner.

Recommended  Ship with no analytics on the site. Substack gives you open rates and subscriber counts for free, which is the only number that will actually change a decision — whether anyone is reading. If you want site numbers later, add a cookieless counter; it is a two-line change.

Decided

Custom domain, on Cloudflare

Yes — buy a domain, register it at Cloudflare, and cut over to it during this rebuild. Cloudflare Registrar sells at wholesale cost with no renewal markup and includes WHOIS privacy, so it is the right registrar for this. Both drbwa.com and brunowassermann.com were unregistered when I checked on 10 September 2026.

On the name itself: drbwa.com is a good handle and it carries real continuity — it is already your identity on GitHub and in the current URL. But it is a handle, not a name. Its job is to survive being said out loud at the end of a conversation at a conference, and "drbwa dot com" has to be spelled out every single time, while "bruno wassermann dot com" does not.

Recommended  Buy both — roughly $10–11 a year each at cost. Make brunowassermann.com the canonical site and redirect drbwa.com to it with a Cloudflare rule. Full setup and the Cloudflare traps are in DOC 04 § 4; the four files that carry the domain are in DOC 02 T1.8.

Decided

Web CV, not a LinkedIn redirect

Build the web CV. Sending people to LinkedIn instead has three real costs: much of a profile is gated behind a login, so a stranger following a link from a paper may hit a wall; it is barely indexable, so it does nothing for anyone searching your name; and it is a page you rent rather than own, laid out by someone else's product team and subject to their redesigns. A CV page you control is text you can point at forever and edit in thirty seconds.

It also resolves R-04: the web CV carries an email address and nothing else. No phone number, no street address, no PDF — the full PDF contains both, and publishing it puts them in front of scrapers permanently. Anyone who needs the signed document can ask.

Recommended  Web CV at /cv/, drafted in DOC 03 § 5.4. Keep the LinkedIn link in the footer — it is where people expect to find the social proof, and it costs nothing to point at both.

Decided

Comments live on Substack

This one is answered by the syndication decision rather than on its own terms. Substack has comments, moderation tools and an audience already signed in; adding giscus to the site would mean maintaining a second discussion surface that requires a GitHub account to use, and putting a third-party script on every post to do it.

Recommended  No comments on the site. The syndicated copy carries the conversation, and the post footer links to it once a Substack version exists — the syndication front-matter field in DOC 05 § 2 is what drives that link. Zero third-party scripts on the site, and the discussion happens where people already are.

Tags and series, or a flat list?

Taxonomy is cheap to add up front and awkward to retrofit once URLs exist.

Recommended  Put an optional tags array in the schema now, but do not build tag pages until there are enough posts to justify them. The schema field costs nothing; ten near-empty tag pages cost credibility.

§ 7

Why not just Substack?

This was raised late and it is the right question to raise, because for a lot of people the honest answer is "yes, just use Substack". It is not the answer here, but the reasons are specific rather than ideological, and worth writing down so the decision does not get relitigated in a year.

A correction to my own earlier advice

My first answer to this argued for staging the work: fix the copy on the existing Jekyll site in about two hours, write one post on Substack, and only green-light the Astro rebuild once there was evidence you would keep writing. That argument priced the rebuild in your hours. It should have priced it in a coding model's hours, with your cost being review time. Once that correction lands, the staging argument mostly evaporates — the marginal cost of building the whole thing properly is small, and deliberately shipping a worse intermediate version to save a cost you were not paying is not a trade-off, it is just a worse site. The full rebuild plus syndication is the right call.

They are not the same product

The site's job
Identity and archive
  • Findable when someone searches your name after reading a paper.
  • Home for the CV, publications and six patents — none of which fit a newsletter.
  • Permanent URLs that a profile, a paper or a talk slide can point at.
  • Evergreen posts that accrue authority to a domain you own.
  • Diagrams, charts and maths authored the way you already work.
Substack's job
Distribution
  • Email, which is still the highest-engagement channel there is.
  • Subscriptions, recommendations and Notes — discovery a static site cannot manufacture.
  • Comments and moderation, already built and already staffed by people who are signed in.
  • Zero maintenance, zero dependency upgrades, zero certificate renewals.

Framed that way the choice dissolves. A newsletter cannot be your CV; a static site cannot build you a mailing list. Doing both is the 2026 consensus for technical writers and it is cheap, because syndication is a copy-paste per post rather than a system.

What Substack genuinely cannot do for your posts

These matter specifically because of the kind of thing you would write — escalation thresholds, cost curves, anomaly-detection results.

  • Maths becomes a bitmap. Substack's LaTeX support covers the equation environment and renders to an image. No inline expressions to speak of, nothing selectable, nothing that reflows.
  • No Mermaid, and no diagram pipeline at all. You would export an image and paste it — workable, but you lose the diagram-as-text living next to the post in version control.
  • Evergreen posts do not rank there. Google indexes Substack shallowly and treats publications closer to news; a post that is still useful in 2032 is worth considerably more on your own domain.
  • You cannot set an external canonical tag. Every Substack post asserts itself as canonical on substack.com. That is exactly why the site has to publish first — see R-07.
  • Platform risk you have already been bitten by. Your analytics died in 2023 and your theme froze years before that. Substack in 2036 is not a given; a directory of HTML files is about as close to one as the web offers.

The caveat that is still true

None of this changes the observation that made the Substack question worth asking in the first place. blog.md has existed in this repository for years, says "A curated list of my blog posts", and lists none. The tooling was never the bottleneck, and a very good publishing pipeline is a very satisfying way to not publish. The rebuild removes every excuse except the real one.

So the measure of whether this was worth doing is not whether the site looks good in October. It is whether there are three posts on it by Christmas.
